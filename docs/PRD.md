# AI 全栈工程师学习平台 · 产品设计文档

> 版本 v1.0 · 对应已交付的 MVP
> 配套阅读：[MVP.md](./MVP.md)（记录了范围取舍的**论证过程**），本文档梳理**产品全貌**。

---

## 一、产品定位

**一句话：** 把互联网上真正免费的优质课程，组织成一条可执行的学习路线，并用自测题和进度追踪确保「学过了」等于「学会了」。

**它不是什么：**

| 不是 | 因为 |
| --- | --- |
| 在线课程平台 | 不生产课程正文，只做策展与导航（规避版权，且已成规模的免费课程做得更好） |
| 视频聚合站 | 视频只是资源的一种形式，文档与交互式教程同样重要 |
| AI 问答工具 | AI 陪练是 V2 的增强项，不是产品本体 |
| 刷题网站 | 自测的目的是「验证掌握」而非「提高分数」 |

**差异性就一句话：** 导航类产品通常只解决「去哪学」，这个产品额外解决了「学完怎么知道我学会了」。

---

## 二、问题定义

做 AI 全栈工程师，卡点从来不是找不到资料 —— 免费优质资料多到看不完。真正的三个卡点是：

| # | 卡点 | 表现 | 本产品的对应解法 |
| --- | --- | --- | --- |
| 1 | **不知道学什么、按什么顺序学** | 收藏了 50 个链接，一个都没打开；不知道 TypeScript 和 RAG 之间还差什么 | 固定 6 阶段路径，明确依赖关系与解锁条件 |
| 2 | **学完不知道会不会** | 视频看懂了，一动手就废 | 每阶段强制自测，答错给解析 |
| 3 | **学着学着就断了** | 三天热度，没有进度感 | 进度可视化 + 一键续学 + 累计投入时长 |

**核心闭环：**

```
今天该学什么 → 打开课程 → 被检验 → 知道自己学会了没 → 知道下一步
```

只要这个闭环成立，内容可以后补；闭环不成立，功能做再多也留不住人。

## 三、目标用户

**主要用户：** 有编程基础、想转型或补齐 AI 应用开发能力的开发者。

- 会写代码，但没系统做过 LLM 应用
- 愿意自己动手，不需要保姆式讲解
- 英文能读但不流畅，因此**中文资源必须是一等公民**

**次要用户：** 在校学生、想了解 AI 工程全貌的技术管理者。

**明确不是目标用户：** 零编程基础的人（第一阶段只补精要，不教编程）。

---

## 四、设计原则

四条贯穿所有功能的原则：

1. **内容外置，机制自建**
   课程正文一律外链，平台只产出「题目」这一种内容。这样资源更新只需改 URL，也不承担内容维护成本。

2. **可解释优先于精确**
   进度规则必须能用一句话说清（「资源做完 + 自测过线 = 阶段完成」）。宁可粗一点，也不要用户看不懂自己为什么是 73%。

3. **降低启动成本**
   每个决策都问「这一步会不会让人放弃」。所以注册只要邮箱密码、推荐默认给最短的资源、未完成时进度条封顶 99% 而不是显示 100%。

4. **验证代替感觉**
   自测、进度、评测数据都是为了让用户（和产品自己）用数字而不是感觉判断「学会了没有」。

## 五、信息架构

```
/                     仪表盘        我在哪 · 下一步学什么 · 一键续学
/login                登录/注册     未登录时的落地页（含产品说明）
/path                 学习路径      6 阶段时间线，展示依赖与解锁状态
/path/:stageId        阶段详情      学习成果 + 资源清单 + 自测入口
/library              资源库        全部资源 + 六维筛选 + 搜索
/quiz/:stageId        阶段自测      答题 → 判分 → 逐题解析
```

**导航层级：** 只有两层（顶层三个入口 + 详情页）。刻意不做多级菜单 —— 产品结构本身足够简单，复杂导航只会增加迷路成本。

**访问控制：** 除登录页外全部需要登录。资源库虽然技术上可以公开，但账号化的进度追踪是核心价值，登录墙换来的是统一的心智模型。

## 六、功能设计

### 6.1 学习路径（6 阶段）

阶段划分的依据不是知识点分类，而是**能力依赖关系**：

| 阶段 | 主题 | 周数 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 | 编程基础精要 | 2 | 不会写 HTTP 服务就调不通 LLM API |
| 2 | LLM 应用核心 | 2 | 第一次把模型接进自己的程序 |
| 3 | 检索增强生成 | 2 | 让模型回答它没被训练过的问题 |
| 4 | 智能体与工具调用 | 2 | 从「一问一答」到「自己决定下一步」 |
| 5 | 工程化与生产 | 2 | 把 demo 变成能交付的东西 |
| 6 | 综合项目实战 | 3 | 拼成作品集里的一个完整产品 |

**解锁规则：** 前一阶段完成度 ≥ 80% 即解锁下一阶段。留这个口子是因为严格串行会让人卡死在一个不感兴趣的阶段上，而 80% 已经足够支撑后续内容。

**每个阶段包含：** 一句摘要、3–5 条「学完你应该能做到」、6–10 个可选资源、一个自测入口。

### 6.2 资源库

**资源字段：** 标题、链接、提供方、语言、难度、形式、时长、主题标签、一句话中文说明、**免费范围说明**。

最后一项是关键：用户点进去才发现要付费，是导航类产品最伤的体验。所以每条资源都必须写清门槛（需注册 / 有免费额度 / 证书付费 / 限时免费）。

**筛选维度**（对齐真实决策场景）：

| 维度 | 取值 | 为什么需要 |
| --- | --- | --- |
| 阶段 | 6 个阶段 | 主线定位 |
| 语言 | 中文 / English | 中文资源质量已够用，不该默认逼人看英文 |
| 难度 | 入门 / 进阶 / 高阶 | 避免新手点进研究向内容 |
| 形式 | 视频 / 文档 / 交互式 / 课程 | 有人只能看视频，有人只看文档 |
| 时长 | ≤3h / ≤10h / ≤20h | 「我有 3 小时」和「我有 3 周」该拿到不同的推荐 |
| 排序 | 路径顺序 / 时长短→长 / 时长长→短 / 标题 | 默认按学习路径排，保证首屏就是「该学的」 |

**当前规模：** 48 个资源（中文 24 + 英文 24），每阶段 6–10 个（基础阶段 10 个，毕业项目阶段 6 个）。筛选器选项的计数基于全量数据统计，不随当前筛选变化 —— 避免「筛完发现想选的选项消失了」。

### 6.3 阶段自测

平台唯一自产的内容，也是与普通导航站的分水岭。

- **形式：** 选择题，一次列出全部题目（题量少，一次看完更好安排时间，也避免「翻到第 5 题想改第 2 题」）
- **规模：** 每阶段 6 题，通过线 80%（即至少答对 5 题）
- **反馈：** 提交后逐题标注对错、给出正确答案与解析；未通过可无限重做
- **记录：** 保存历史最好成绩（而不是最后一次），避免手滑重做把成绩刷低

**出题原则：** 考理解与判断，不考 API 记忆。错误选项必须是「看起来合理的常见误解」，例如「temperature=0 输出就确定了」「上下文满了就静默截断最早的几条」——这些是真实会踩的坑，而不是凑数的干扰项。

**安全设计：** 下发给前端的题目**永不含答案与解析**，判卷在服务端完成。否则打开 DevTools 就能看到答案，自测就失去了意义。

### 6.4 进度系统

**三种状态：** 想学 / 在学 / 已完成。一颗星到三颗星的复杂度，不多不少。

**完成规则：**

| 概念 | 规则 | 设计意图 |
| --- | --- | --- |
| 阶段完成 | 该阶段资源全部标记已完成 **且** 自测通过 | 「看完」和「会了」都不能少 |
| 阶段完成度 | 资源占比 75% + 自测得分率 25% | 两件事都重要，但资源投入更耗时 |
| 未完成封顶 | 最高显示 99% | 避免「进度条 100% 但阶段没完成」的困惑 |
| 无题库阶段 | 完全按资源算 | 否则会出现「一个资源没开始却显示 25%」 |
| 阶段解锁 | 前一阶段完成度 ≥ 80% | 允许提前窥探，避免卡死 |

**云端同步：** 进度存服务端并绑定账号，换设备接着学。所有进度接口都做了用户隔离（有测试断言 A 用户的操作不会出现在 B 用户的仪表盘里）。

### 6.5 账号

- **注册：** 邮箱 + 密码（≥8 位）+ 可选昵称。没有邮箱验证、没有手机号、没有第三方登录 —— 学习类产品最大的流失点就是第一次打开的注册墙
- **认证：** httpOnly cookie + JWT，前端 JS 读不到会话（降低 XSS 窃取风险）；开发时靠同源代理，`SameSite=Lax` 即可挡住 CSRF
- **安全细节：** 登录失败时「邮箱不存在」与「密码错误」返回**同一句提示**，避免账号枚举

### 6.6 仪表盘

用户每天打开的第一屏，回答三个问题：

1. **我在哪** —— 总体进度、已完成阶段、通过自测数、累计投入时长
2. **下一步学什么** —— 「继续学习」卡片：优先推荐最近标记为「在学」的资源；没有则推荐当前阶段里**最短**的未完成资源（降低启动成本）
3. **整体节奏如何** —— 6 个阶段卡片，一眼看到全局

## 七、核心用户旅程

**首次使用（目标：3 分钟内开始学第一个资源）**

```
落地登录页（左侧直接展示 6 阶段路线，先讲清价值）
  → 注册（邮箱 + 密码，两个字段）
  → 仪表盘（自动给出「继续学习」推荐，无需自己挑）
  → 点开课程外链，开始学
```

**日常使用（目标：10 秒内回到上次的位置）**

```
打开仪表盘 → 看到「继续学习」→ 一键打开
```

**阶段收尾（目标：明确知道自己能不能进下一阶段）**

```
阶段页看到资源清单 → 逐个标记完成 → 进度条推进
  → 做自测 → 未通过则看解析重做 / 通过则进入下一阶段
```

## 八、关键设计决策

| 决策点 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 课程正文 | 外链，不落库 | 规避版权 + 零内容维护成本 | 用户体验有跳转断层；无法控制外站质量变化 |
| 完成判定 | 资源 + 自测双重条件 | 只算资源会变成「收藏家」，只算自测会跳过学习 | 完成一个阶段的心理成本较高 |
| 进度展现 | 百分比 + 封顶 99% | 可解释，且不会误导 | 不是精确的「完成了几分之几」 |
| 答案位置 | 只在服务端 | 防止 DevTools 直接看答案 | 无法支持纯离线模式 |
| 认证方式 | httpOnly cookie | 前端读不到会话，比 localStorage 存 token 更安全 | 前后端分域部署时需要额外处理（当前靠 Vite 代理同源） |
| 前端状态管理 | 自写 30 行 hook | 只需「加载 + 重试 + 刷新」，不引额外依赖更好讲清 | 缺少缓存与自动重验证，后续复杂起来需要换 |
| 数据库 | Node 内置 node:sqlite | **零原生依赖**，Windows 上不需要编译工具链 | 不适合多实例水平扩展（当前量级完全够） |
| 密码哈希 | Node 内置 scrypt | 同上，且 scrypt 本身抗 GPU 暴力破解 | 缺少 argon2 的抗侧信道调优参数 |

## 九、数据模型概览

| 实体 | 说明 | 关键约束 |
| --- | --- | --- |
| `users` | 账号 | 邮箱唯一；密码只存 scrypt 哈希 |
| `resources` | 外部免费课程 | 只存元信息与链接，不含正文 |
| `quiz_questions` | 自测题 | 选项与答案下标；**下限校验**：每阶段至少 5 题 |
| `progress` | 用户 × 资源 的状态 | 复合主键，天然幂等 |
| `quiz_attempts` | 作答历史 | 用于计算历史最好成绩 |

**数据完整性由三道防线保证：** 数据库外键约束 → 种子数据校验（链接必须 https、答案下标不能越界、每阶段最少条数）→ 单元测试断言。

## 十、成功指标

**北极星指标：** 用户连续 7 天产生有效学习行为（打开课程外链 / 标记进度 / 提交自测）。

不选「注册数」是因为它不反映价值；不选「总学习时长」是因为难以准确采集。7 天连续是很低但很诚实的门槛。

**分层指标：**

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 获客 | 注册转化率 | 登录页停留 → 注册完成 |
| 激活 | 首次学习耗时 | 注册到第一次打开课程外链的时长，目标 < 3 分钟 |
| 留存 | D7 留存 / 续学点击率 | 仪表盘「继续学习」的点击率是最灵敏的先行指标 |
| 价值 | 阶段自测通过率 | 过低说明题目太难或资源没讲清，过高说明题目太水 |
| 结果 | 阶段完成率 / 毕业项目完成数 | 最终目标 |

**特别注意：** 自测通过率要在 60%–85% 之间才算健康。低于 60% 是内容或题目有问题，高于 85% 说明自测没有区分度、在浪费时间。

## 十一、版本规划

### V1（已交付）

学习路径 + 资源库（筛选搜索）+ 阶段自测 + 进度同步 + 账号 + 仪表盘。

### V1.1（低成本高收益）

| 功能 | 为什么优先 |
| --- | --- |
| **死链检测** | 定时任务检测资源 URL 存活并告警。成本极低，但直接决定资源库的可信度 |
| 题库扩充 + 随机抽题 | 当前每阶段固定 6 题，重复作答会记住答案，自测失去意义 |
| 免费范围定期复核 | 部分资源是「限时免费」，需要机制保证说明不过期 |

### V2（需要新能力）

| 功能 | 价值 | 前置条件 |
| --- | --- | --- |
| **AI 陪练** | 直接解决「卡住没人问」，是闭环上最大的缺口 | 需要 LLM API、成本控制、失败降级 |
| 学习笔记 | 把「学过的」变成「能讲出来的」，也便于面试复习 | 富文本编辑与存储 |
| 代码沙箱 | 把「看懂」变成「写出来」 | Monaco + 隔离执行环境，工程量最大 |

### V3（需要规模）

- 资源社区投稿 + 人工审核（解决策展的可持续性）
- 多路径 / 个性化推荐（当前单一路径是刻意的简化）
- 评测驱动的内容迭代：用答题数据定位「大家都答错的题」，反推是题目有问题还是资源没讲清楚

## 十二、已知风险与开放问题

**风险：**

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 外部资源失效或改为付费 | 核心资产贬值 | `verified` 字段 + notes 说明门槛；V1.1 补死链检测 |
| **「收藏夹吃灰」** | 用户标记了「想学」但从不开始 | 仪表盘的「继续学习」推荐刻意选**最短**的资源，降低启动成本 |
| 资源集中在少数提供方 | 单一来源失效影响面大 | 调研时已刻意分散（官方文档 / 大厂课程 / 开源社区） |
| 免费标注有实效性 | 用户点进去发现要付费 | notes 写明「限时免费」等字样，需定期复核 |

**开放问题（尚未有答案）：**

1. **单一路径 vs 多路径** —— 现在只有一条刚性路线。对已经有部分基础的人（比如会 React 但不懂 RAG），是否可以跳过阶段？跳过就破坏了「依赖关系」这个立论。
2. **自测能否替代真正的动手** —— 选择题可以验证概念，但验证不了「能不能写出来」。代码沙箱是不是必须的，而不是锦上添花？
3. **里程碑奖励是否必要** —— 当前没有任何游戏化元素。对自驱型用户是减负，对需要外部激励的用户可能不够。
4. **资源质量如何持续评估** —— 现在靠人工策展。能否用用户的完成率与自测成绩反向给资源打分？会不会形成偏见循环（难的资源被系统性地打低分）？
